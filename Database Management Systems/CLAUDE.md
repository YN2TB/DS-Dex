**Status: ✅ COMPLETE.** `contents/00-Index.md` + **all 11 chapters written, with every SQL statement executed against a real database and the actual output printed.**

## Findings so far

- **Ch. 01:** the three anomalies are *demonstrated*, not described — a real SQLite table, a partial `UPDATE` leaving one agent with two contradictory phone numbers, a `DELETE` of one customer silently destroying an agent (2 distinct agents → 1), then the split-table fix removing all three. **Two things the book does not contain:** the insertion anomaly presents as an outright `NOT NULL` rejection under a strict schema rather than as a dummy row (so **constraints convert corruption into errors**), and **SQLite ignores `REFERENCES` unless `PRAGMA foreign_keys = ON`, which is OFF by default and per connection** — a correct-looking schema can enforce nothing. Framing used throughout: **normalisation restricts representable *states*, not answerable *questions*** (a join reconstructs the flat view exactly).
- **Ch. 02:** all eight relational-algebra operators **executed in SQL**, plus the identity $R\bowtie S=\pi(\sigma(R\times S))$ verified by computing both sides (identical). C&M treats the algebra as vocabulary, so this chapter is heavily enriched. **New SQLite findings, both mine:** `TEXT PRIMARY KEY` accepts **multiple NULLs** (two identity-less rows), and `INTEGER PRIMARY KEY` **auto-assigns** on NULL even under `NOT NULL` — it *fabricated a phantom vendor* inside my own demo. Fix: explicit `NOT NULL` on a non-integer key, or a **`STRICT` table**. **With ch. 01's `PRAGMA foreign_keys` finding: SQLite enforces neither integrity rule by default.** Also documented: SQL is bags not sets (7 rows vs 4 with `DISTINCT`), inner joins drop rows silently (7 products in, 6 out), DIVIDE via $\forall x P \equiv \neg\exists x\neg P$.
- **Ch. 03:** every ER construct given as **executable `CREATE TABLE`, not diagrams** — the right call, since this chapter is the worst-hit by lost figures (the diagrams *are* the content) and a schema shows what a diagram cannot: whether a constraint is actually enforced. **Centrepiece is the fan trap, executed:** per-team counts of **3, 3, 1 in a 4-player league** (7 join rows), correct answers 2, 1, 1. **My own finding: the trap is not uniformly wrong** — singleton groups come out right, so spot-checks pass. Also demonstrated: redundant relationships letting two join paths contradict while every FK stays valid; a list-in-a-cell where exact search returns **0 rows on present data**; and an unplanned but better lesson — `ON DELETE CASCADE` on the weak entity was blocked by the *recursive* `mgr_id` FK, so each FK needs its own referential action.
- **Ch. 04:** every FD **detected** by `GROUP BY … HAVING COUNT(DISTINCT …) > 1` rather than asserted — **and the scan produced two false positives on C&M's own example** (`chg_hour → job_class`; `hours` reported as a candidate key), giving the chapter's best idea: **the test can only refute, never confirm — confirm against business rules.** **C&M omits lossless join and dependency preservation entirely**, so §5 and the 3NF/BCNF trade table are additions: a lossy split on the non-key `job_class` turned **8 triples into 13, fabricating 5**, which is ch. 03's fan trap in formal dress. Unifying rule: **a join is only meaningful when its key identifies rows in at least one table.** 3NF is always lossless *and* dependency-preserving; BCNF only the former — hence 3NF is the target. Denormalisation measured honestly at **1.6×** (0.1698s → 0.1075s) for storing one rate **4 104 times instead of once**.
- **Ch. 05:** reframed away from C&M's syntax tour toward **what fails silently**. Centrepiece is the **`NOT IN` trap** — one NULL in the list makes the query return the empty set *for any data* (verified: 0 rows where the answer was Legal); C&M never mentions it. Also mine: the **three-valued truth tables**, the fact that **a condition and its negation don't partition a table** (3 rows + 0 rows out of 6), **`AVG(bonus)` 5333 vs `AVG(COALESCE(bonus,0))` 2667** — a factor of two turning on whether NULL means "none" or "unknown" — and the **clause evaluation order** (`FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY→LIMIT`), which C&M omits entirely though it explains most of SQL's apparently arbitrary rules.
- **Two self-corrections in ch. 05, both recorded in the note:** the `NOT IN` demo first used a department that *did* have an employee, so the correct answer was also 0 rows and **the trap proved nothing** (fixed by adding an employee-less `Legal`); and the evaluation-order demo assumed an alias in `WHERE` would be rejected — **SQLite accepted it**, so it was swapped for an aggregate in `WHERE` and the deviation reported as its own finding.
- **Ch. 06 — most heavily enriched so far** (C&M is thin on window functions, as the subject file predicted). **Best finding, and I haven't seen it in an intro DB text: the default window frame is `RANGE`, not `ROWS`**, so `SUM(x) OVER (ORDER BY d)` silently mis-computes running totals whenever `d` has duplicates — verified **6300 vs 4800** on a tied row, with the *final* total still correct so spot-checks pass. Also: **correlated subquery → window function = 3068× faster** (51.13s → 0.0167s), `ROW_NUMBER` nondeterministic without a tiebreaker, and top-N-per-group as the portable fix for ch. 05's bare-column trap.
- **Ch. 06 benchmark failed TWICE before giving the right answer** — `LIMIT 5` let the correlated form stop early (said window was 3.6× *slower*); then `SELECT COUNT(*)` let the optimiser discard the work entirely (0.0000s). Fixed by consuming the value with `SUM()`. **Four SQL-benchmarking hazards now recorded in the note: avoid `LIMIT`, consume the result, take the minimum of runs, check `EXPLAIN QUERY PLAN`.**
- **Ch. 07 is the least verifiable chapter** (C&M ch. 9 is pure methodology — phases and checklists). **Deliberately kept the process sections compact rather than padding with invented demos**, and put the effort into the one testable thing: **an audit of 10 stated business rules, finding the schema enforces 6.** That produced a taxonomy I haven't seen in an intro text — the **three constraint classes `CHECK` cannot express**: (i) minimum cardinality on the "one" side, (ii) aggregate constraints (needs a COUNT over other rows), (iii) transition constraints (restricts old→new, but CHECK sees only new). Each verified as unenforced. **Also chose NOT to quote a speed-up ratio in §6** because the indexed time fell below timer resolution — quoted the query plan (`SCAN`→`SEARCH USING INDEX`) instead.
- **Ch. 08:** produced a **real lost update with 5 threads — 100 bookings committed, 20 seats consumed, 80 sold twice**, no error and no constraint violated. C&M only tabulates a schedule; executing it is far stronger. **The key correction to a common misconception, and C&M states the isolation table and the lost-update problem in the same chapter without connecting them: NO isolation level fixes this**, because read and write are in *different* transactions — raising it is a costly no-op that can *hide* the bug. Both fixes verified: atomic `SET x = x - 1` (0 lost, no rejections) and optimistic locking with a version column (0 lost, **14 retries**, final version 101 proving no write vanished).
- **Ch. 08 method note:** the first variant put the read *inside* the transaction — SQLite then prevented every lost update **by rejecting 51 of 100 bookings** (`database is locked`). **Kept that result in the note** rather than discarding it: it demonstrates the isolation/throughput trade better than any prose. Realistic lost update needed read-outside-transaction (the web-app pattern).
- **⚠️ SQLite is *stricter* than PostgreSQL here** — first such case, after four permissivenesses. `SERIALIZABLE` only, via a **whole-database** write lock, so unrelated writers still conflict. WAL mode fixes reader/writer contention (verified).
- **Ch. 09 — the most measurable chapter; C&M gives no numbers at all.** On 400k rows (sized so timings clear the clock, correcting ch. 07 §6): **755×** index vs scan · **65×** between selective and unselective filters *on the same index* · **~1000×** for a non-sargable `LOWER(col)` predicate · **66×** for a covering index · **29× write penalty** for 7 indexes. The DSA cross-links carry the *explanations* C&M asserts: **DSA ch. 10 §7** (B-trees, block transfers, why locality not comparison count), **ch. 09** (why hash indexes can't do ranges), **ch. 11** (external merge-sort behind sort-merge joins). Also completed ch. 02's argument: **the optimiser's freedom follows from the algebra constraining only the *result*, and closure is what licenses filter pushdown.**
- **Ch. 09 reports two honest limits rather than glossing them:** `ANALYZE` changed *neither* plan (the `COUNT(*)` queries were covering-index-answerable, so nothing discriminated), and §2's two selectivity queries *both* used the index for the same reason — so the scan/index crossover was inferred, not observed. **Flagging what wasn't demonstrated is part of the demonstration.**
- **Ch. 10 — where the subject meets the rest of the degree.** Two results, both mine: **SCD Type 1 retroactively changed 2023/2024 revenue by exactly the moved customer's totals** (−22 019, −34 460) — published reports become non-reproducible, which breaks audit *and* point-in-time correctness for model training; and **joining facts on the business key instead of the surrogate key inflated revenue by exactly the double-counted customer (78 502)**. That is the **third instance of one rule** (fan trap ch. 03, lossy decomposition ch. 04): *a join is only meaningful when its key identifies rows in at least one table* — and note **implementing Type 2 retroactively invalidates any query joining on the business key.** Also completed ch. 04's argument: warehouse denormalisation is safe because **nothing updates in place**, so the anomaly is prevented by *process*, not structure.
- **Ch. 10 self-correction, recorded in the note:** the first Type 1 demo hardcoded region `North` while the generated data put the customer in `Central`, so **the measured change was 0,0,0 while the narrative asserted history had changed** — claim contradicted its own output. Same failure DSA logged five times. Fixed by reading the actual region from the data.
- **⚠️ SQLite lacks `ROLLUP`/`CUBE`/`GROUPING SETS`** (verified) — subtotals need `UNION ALL`, one pass per level. **Second SQLite *limitation*** (after ch. 08's whole-database lock), as distinct from the four *permissivenesses*.
- **Ch. 11 (last) — most heavily enriched chapter** (C&M ch. 14 is an industry survey; the subject file predicted this). Centrepiece is **the three costs of "schemaless", all verified**: a string price silently coerced to 0 so `SUM` gave **2123 against a true 2148**; a document missing `category` vanishing from every filtered report; and `category`/`Category`/`cat` hiding **2 of 7** matching products. **`json_each` found twelve field names in a five-field collection** — the schema exists, written by nobody. Framing: **"schemaless" means the schema moved into the application, unenforced** — ch. 07's finding at full strength. Also: document queries **6.7× slower unindexed, 3.1× indexed**, and **indexing a document field requires knowing its path, so flexibility is surrendered exactly where performance matters.**
- **Ch. 11 §9 states explicitly what could NOT be demonstrated** (SQLite is single-node): sharding, replication, real CAP partitions, eventual consistency, column-family layout, index-free adjacency. **Better than faking a cluster** — and it yields the chapter's most useful judgement: NoSQL's real advantages live in distribution, so adopting it on one machine buys the costs and none of the point.
- **⚠️ FIFTH SQLite permissiveness, found incidentally in ch. 11:** a `REAL NOT NULL CHECK (price >= 0)` column **accepted the string `'twenty five'`** — type affinity does not enforce declared types. PostgreSQL rejects it.
- **The subject's connecting theme, now three-way:** a **diagram** promises more than a schema delivers (ch. 03) · an **engine** delivers less than its DDL claims (ch. 01/02/05, SQLite) · a **requirements list** promises more than any schema can deliver (ch. 07). **Remedy is always the same: try to violate the constraint.**
- **⚠️ Running tally now at FOUR SQLite permissivenesses** (keep extending this — it's a genuine through-line): FKs off by default (ch. 01); `PRIMARY KEY` accepts NULLs and `INTEGER PRIMARY KEY` auto-assigns (ch. 02); alias in `WHERE` accepted (ch. 05); bare column with an aggregate accepted, value arbitrary (ch. 05). **In every case SQLite returns a result where PostgreSQL raises an error.**
- **Recurring theme across ch. 01–05, my framing:** **an ER diagram promises more than a schema can enforce** (minimum participation, completeness constraints), and **SQLite enforces less than its DDL claims**. Test constraints; don't read them.
