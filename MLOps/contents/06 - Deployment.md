# ML System Deployment

> [!note] Where this sits in the course
> The **fourth stage** of the ML lifecycle. [[05 - Packaging Models with FastAPI and Docker]] put the model in a container; this chapter decides **where it runs, when it predicts, and how it is released** — and confronts **model risk**, the governance question of what happens when it is wrong.

## 📘 Main Knowledge

> At the deployment and integration stage, the trained model is **integrated into production systems and workflows**.

### Two categories of challenge

- **Software engineering issues** — system compatibility, scalability, operational constraints.
- **Statistical issues** — data drift and concept drift.

The split matters because the two need different people and different tools. Neither alone is sufficient — and the second has no analogue in ordinary software deployment.

> **User requirements and constraints drive system design; system design drives selection of technologies.**

**System design decisions that determine technology choice:** computing resources (CPU/GPU/memory) · **latency and throughput** · logging · privacy and security.

---

### Cloud vs Edge AI

**Edge AI** runs machine learning **directly on devices**, enabled by solving power constraints, increased edge computational power, and smaller models designed for edge deployment.

> **Why Edge AI? It eliminates latency.** Every 100 miles from a datacenter introduces **> 1.6 ms** of latency.

| Aspect | **Cloud ML** | **Edge ML** |
|---|---|---|
| Description | Computation in the cloud, results sent to devices | Computation directly on the device |
| Requirements | Network connectivity | Sufficient local compute and memory |
| Benefits | High throughput | **Low latency, privacy, offline operation** |
| Examples | Chatbots, demand prediction | Quality control, autonomous driving |

**Hybrid approaches:** initiate cloud-based ML through triggers generated by edge AI · store common pre-computed predictions locally · exploit multiple local datacenters to minimise latency. *The smart speaker is the canonical example — wake-word detection on-device, full speech understanding in the cloud.*

**Three questions decide it:**
- **How much does latency matter?** A lot → Edge. Not much → Cloud.
- **Is reliance on internet connectivity acceptable?** No → Edge. Yes → Cloud.
- **Are users comfortable sending their data to the cloud?** No → Edge. Yes → Cloud.

Edge deployment is where the **quantization, pruning, and compression** of EdgeOps ([[01 - Introduction to MLOps]]) become necessary.

---

### Offline vs online *learning*

**Online learning:**
- Looks at **a single data point at a time**
- Makes a small **incremental update** to the model with each new point
- **Gradually improves** as more data arrives

*Online learning uses data in motion.* It is how a system adapts continuously rather than in discrete retraining cycles.

### Batch vs online *prediction*

> A separate axis from learning. A model can be trained offline and serve online, which is the most common arrangement.

**Batch (offline) prediction:**
- Generate predictions on a **batch of observations**
- Jobs run on a **recurring schedule**
- Predictions are **stored in a database** and made available to developers or end users
- **Latency is often not a concern**
- **Predictions are not available for real-time purposes**

**Online prediction:**
- Generates predictions **in real time upon request**
- Jobs are generated as soon as needed and served immediately
- **More complex** because of the added tooling required to meet latency requirements: retrieving necessary features, inference time, validating model output, web technologies

*Recommendation systems* typically use batch prediction; *food delivery "time-to-arrive"* requires online prediction.

---

### Big Data and system design

**The three Vs:**
- **Volume** — the amount of data, in both number of points and number of variables per point
- **Velocity** — the speed of data accumulation
- **Variety** — data in different forms (image, audio, text) that changes over time

**Unique challenges:** massive storage needs · processing computational costs · understanding quality, patterns, and relationships · **data too large to fit in memory**.

---

### Preparing for deployment

**Production environments:**
- **Custom-built services**
- **Data science platforms / dedicated services** — TensorFlow Serving
- **Low-level infrastructures** — Kubernetes clusters → [[07 - Kubernetes for ML Deployment]]
- **Embedded systems** — JVMs

> **Perform validation in an environment that mimics production as closely as possible, rather than in the development environment**, to minimise adaptation work and improve the chances that the model behaves in production as it did in development.

This is the argument for Dev Containers and identical images across environments from [[02 - Environment Setup]].

### Model risk

> **Model risk** occurs when a model is used to measure and predict quantitative information but **performs inadequately**. Poor performance can result in **regulatory scrutiny, legal non-compliance, and significant reputational and financial losses.**

> Uncomfortable questions need to be answered: *What if the model acts in the worst imaginable way? What if a user manages to extract the training data or the internal logic?*

**Sources of model risk:**

| Source | Description | Example |
|---|---|---|
| **Data** | Input data erroneous, incomplete, outdated, or biased | Outdated market data projects skewed price trends; a hiring algorithm trained on a homogeneous male workforce favours male candidates |
| **Assumptions and variables** | Unrealistic assumptions alter intended parameters; irrelevant, wrong, missing, or omitted variables; incorrect calibration | |
| **Methodology** | Inherent errors in the method | Regression modelling has sampling errors and standard errors |
| **Model implementation** | Incorrect or incomplete implementation, programming errors, approximation mistakes | |
| **Interpretation** | Misreading the output leads to misinformed decisions | |
| **Model usage** | Inappropriate use invalidates an otherwise effective model | A model that identifies a lung condition **in children** applied to adults |

That last row is the subtlest: the model is correct, the implementation is correct, and the deployment is still wrong because it is used outside the population it was built for.

**Evaluation and management process:**

1. **Catalogue all models** — understand their purpose, data, assumptions, and potential risks.
2. **Assessment and validation:**
   - *Quantitative* — statistical methods (simulation, extreme value theory) to test accuracy and performance
   - *Qualitative* — expert judgment on design, assumptions, and suitability for intended use
   - *Data Quality* — profiling for inconsistencies and missing values
3. **Mitigation** — performance monitoring, risk limits, user training, robust governance.

**Worked example — credit scoring.** A bank approves or rejects loans from applicant data (income, credit history, employment).

| Risk | Issue | Evaluation |
|---|---|---|
| **1. Data** | Training data outdated, not reflecting recent economic conditions → underestimates default risk in downturns | Compare training vs recent distributions; detect **data drift** in income and employment features |
| **2. Model (statistical)** | Overfits historical patterns → poor generalisation to new applicant profiles | Cross-validation; **stress testing with synthetic edge cases**; performance stability across time slices |
| **3. Concept drift** | Borrower behaviour changes after policy or interest-rate changes | Monitor default rates by prediction bucket; track **Population Stability Index (PSI)** |
| **4. Operational** | Feature pipeline mismatch between training and production | **Training–serving skew checks**; end-to-end pipeline validation |
| **5. Ethical / Compliance** | Decisions correlate with protected attributes → discriminatory lending | **Fairness metrics** (disparate impact); **explainability audits (SHAP)** |

> **Takeaway: model risk extends beyond accuracy to data quality, robustness, deployment, and ethics.**

### Deployment approaches

**Shadow deployment (mirroring)** — the new model runs in production **alongside** the existing one, and performances are compared **without affecting user-facing results**.

| | |
|---|---|
| **When** | Evaluate a new model without affecting users · compare predictions against production · regulatory or safety constraints prevent user impact |
| **Best for** | Model validation and monitoring · **risk-sensitive domains (finance, healthcare)** |
| **Limitations** | **No user feedback** · **doubles inference cost** |

**Canary deployment** — rolled out first to **a small subset** of users or traffic; if it performs well, gradually rolled out to the entire infrastructure.

| | |
|---|---|
| **When** | Gradual rollout to a small subset · need to monitor real-world performance and stability |
| **Best for** | Online prediction systems · **A/B testing model improvements** |
| **Limitations** | Requires traffic routing and monitoring infrastructure · **small failures still affect some users** |

**Blue–Green deployment** — two identical environments (**blue** = current, **green** = new) run simultaneously; traffic switches **entirely** once green is fully tested. **Quick rollback** by switching back to blue.

| | |
|---|---|
| **When** | Need **zero downtime** · want a **fast rollback** option |
| **Best for** | Stable, well-tested models · predictable workloads |
| **Limitations** | **Higher infrastructure cost** (duplicate environments) · less effective for real-time performance evaluation |

**Rolling deployment (phased rollout)** — gradually deploy new versions by **slowly replacing the infrastructure**. Quicker than blue–green, but **rollback is more complicated**.

| | |
|---|---|
| **When** | Continuous updates with minimal resource overhead · downtime acceptable at a micro level |
| **Best for** | Large-scale distributed systems · frequent updates |
| **Limitations** | **Harder rollback** · temporary inconsistency across instances |

| Scenario | Recommended Strategy |
|---|---|
| Safe offline evaluation without user impact | **Shadow** |
| Gradual rollout to a subset of users | **Canary** |
| Zero downtime with fast rollback | **Blue–Green** |
| Continuous updates at large scale | **Rolling** |

> **There is no single best deployment strategy** — the right choice depends on **risk tolerance, system criticality, and monitoring maturity**.

---

### A/B testing

> Compare the performance of different models or versions **in a controlled manner**, randomly assigning users or requests to variants to gather **statistically significant** results on model performance, user engagement, or business metrics.

**The six steps** — a direct application of [[Mathematical Statistics/contents/07 - Hypothesis Testing - One Sample|hypothesis testing]]:

1. **Pose the question** — do visitors to sites A and B convert at different rates?
2. **Specify $H_0$ and $H_1$** — $H_0$: conversion rate is the same; $H_1$: it differs.
3. **Choose a test and significance level** — z-test, $\alpha = 0.05$.
4. **Collect data** — track visitors over a period, **randomly assigning** each to A or B.
5. **Run the test** — compute the test statistic and p-value.
6. **Evaluate the results.**

**Randomisation is what makes it causal.** Because assignment is random, the two groups differ only by chance, so a significant difference is attributable to the variant rather than to a confound — the distinction [[Mathematical Statistics/contents/03 - Descriptive Statistics|correlation vs causation]] warns about.

## ✏️ Exercises

**1.** *(Slide 15 quiz)* Classify each as best suited to **Cloud AI** or **Edge AI**: (1) autonomous drone navigation; (2) facial recognition on a smartphone; (3) chatbot serving millions; (4) industrial robot collision avoidance; (5) monthly retail sales trend analysis.

> [!example]- Solution
> | # | Application | Answer | Deciding factor |
> |---|---|---|---|
> | 1 | Autonomous drone navigation | **Edge** | Latency + connectivity |
> | 2 | Facial recognition on smartphone | **Edge** | Privacy + latency |
> | 3 | Chatbot for millions | **Cloud** | Throughput, large model |
> | 4 | Industrial robot collision avoidance | **Edge** | Safety-critical latency |
> | 5 | Monthly sales trends | **Cloud** | No latency constraint |
>
> **(1) and (4) are decided by latency and physics.** A robot moving at 2 m/s travels 4 mm in the 2 ms a round trip to a nearby datacenter costs — and much further over a real network. Worse, both must keep working when connectivity drops; a drone that stops navigating when WiFi fails crashes. Safety-critical control **cannot depend on a network**.
>
> **(2) is decided by privacy.** Face data is biometric; users are not comfortable transmitting it, and regulators increasingly forbid it. This is the third of the deck's three questions, and it is why phone face-unlock runs entirely on-device.
>
> **(3) is Cloud for the opposite reasons.** A large language model does not fit on a phone, throughput across millions of users demands elastic server capacity, and a few hundred milliseconds is imperceptible in conversation.
>
> **(5) is trivially Cloud** — a monthly batch job has no latency requirement at all, and pairs naturally with **batch prediction**.
>
> **The pattern: latency and connectivity push to the edge; model size and throughput pull to the cloud; privacy pushes to the edge.** Note that (1), (2), and (4) all also require the model compression of EdgeOps — a full-size model will not run on a drone.

**2.** *(Slide 24 quiz)* Classify each as **batch** or **online prediction**: (1) real-time fraud detection; (2) autonomous vehicle perception; (3) daily sales forecasting; (4) voice assistants; (5) YouTube recommendation.

> [!example]- Solution
> | # | System | Answer |
> |---|---|---|
> | 1 | Real-time fraud detection | **Online** |
> | 2 | Autonomous vehicle perception | **Online** (and edge) |
> | 3 | Daily sales forecasting | **Batch** |
> | 4 | Voice assistants | **Online** |
> | 5 | YouTube recommendation | **Batch** (mostly) |
>
> **The test is: does the input exist before the request?** For fraud (1), the transaction *is* the request — it cannot be predicted in advance, and the answer is needed within the sub-100 ms window from [[01 - Introduction to MLOps]]. Same for (2) and (4): the sensor frame and the spoken utterance arrive with the request.
>
> **(3) is batch** because tomorrow's forecast can be computed overnight and stored. Nothing about it needs to be live, and batch is simpler and cheaper — the deck notes online prediction is *"more complex because of the added tooling and systems required to meet latency requirements."* **Choose batch whenever the use case permits it.**
>
> **(5) is the interesting one.** YouTube recommendation is *mostly* batch: candidate videos for each user are precomputed on a schedule and stored, because scoring millions of videos against millions of users per request is infeasible. Serving then retrieves the precomputed list in milliseconds. But real systems are **hybrid** — a lightweight online re-ranking layer reorders the precomputed candidates using session context (what you just watched). This is exactly the deck's hybrid pattern: *"store common pre-computed predictions locally"*.
>
> **Note the two axes are independent.** (2) is online prediction *and* edge deployment; (1) is online prediction *and* cloud. And per [[03 - Data in MLOps]], batch/stream **ingestion** is yet a third axis — fraud needs stream ingestion *and* online prediction, while sales forecasting uses batch ingestion *and* batch prediction.

**3.** *(Slides 50–51 quizzes)* (a) Which is the more accurate description of deployment — a high-stakes event to get right immediately, or an iterative process? (b) A bank logs a loan model's output but a human officer decides. What deployment type is this?

> [!example]- Solution
> **(a) Answer: 2 — it is an iterative process** where you should expect multiple adjustments (metrics monitored on dashboards, percentage of traffic served) to work toward optimising the system.
>
> Option 1 is the tempting answer and it is wrong, for a reason this course has established repeatedly. You **cannot** design a system that works reliably immediately after launch, because production reveals things development cannot: the real input distribution, real traffic patterns, real edge cases, and real user behaviour that changes in response to the model. [[01 - Introduction to MLOps]] made the same point — *"fraud detection is not a one-time model, but a continuous system"* — and the ML lifecycle is explicitly **iterative, not linear**.
>
> The deployment strategies in this chapter exist *because* of this. Canary and shadow are mechanisms for **learning from production incrementally** rather than betting everything on a single launch. Believing option 1 leads to the anti-pattern of extensive pre-launch engineering followed by a big-bang release with no rollback path.
>
> **(b) Answer: 1 — Shadow model deployment.** The definition given: *"Shadow is a type of deployment where the ML algorithm runs in parallel with the user but its output isn't used for any decision making."*
>
> The key detail is that **output is logged for analysis but drives no decision**. That is precisely shadow deployment's purpose, and lending is exactly the *"risk-sensitive domain (finance, healthcare)"* it is recommended for. The bank gets real-world performance data on real applicants at **zero risk to applicants** — and, valuably, the human officer's decisions become ground-truth labels to evaluate against.
>
> Not canary (no user subset receives model-driven decisions), not blue–green (no traffic switch — the model never serves), not rolling (nothing is being replaced).
>
> The trade-off is the deck's stated limitation: **no user feedback**. You learn whether the model agrees with loan officers, not whether its approvals would actually have been repaid — the counterfactual is unobservable because the model's decisions were never acted on.

**4.** Using the credit scoring example, explain why **operational risk** (item 4) can defeat a model that passes every statistical check.

> [!example]- Solution
> **The issue is a feature pipeline mismatch between training and production**, and the deck's phrasing is exact: *"Incorrect predictions **despite a good model**."*
>
> The model is genuinely good. Cross-validation is strong, it generalises across time slices, fairness metrics pass. **And it is still wrong in production**, because the features it receives are not the features it was trained on.
>
> **How it happens.** Training computes `debt_to_income` from a warehouse table where `income` is annual. The production service reads from a live API where `income` is monthly. Both pipelines are correct in isolation; nobody wrote a bug. But the model now sees ratios twelve times larger than any it trained on, and confidently produces nonsense. Other variants: a categorical encoded with a different category ordering, a feature computed over a 30-day window in training and 7 days in serving, or a null imputed with the median in one path and zero in the other.
>
> **Why statistical validation cannot catch it.** Every check in items 1–3 evaluates the model **on the training pipeline's data**. Cross-validation, stress testing, and drift monitoring all consume features produced by the *training* path. The defect lives in the *serving* path, which validation never touches.
>
> It is also **silent** — no exception, no schema error, just wrong numbers. And it can look like drift: default rates diverge from predictions, so the team retrains, which does nothing because the model was never the problem. This is the distinguish-drift-from-bugs discipline of [[01 - Introduction to MLOps]].
>
> **The defences the deck names:** **training–serving skew checks** — take the same input through both pipelines and assert the feature vectors are identical — and **end-to-end pipeline validation** rather than validating the model alone.
>
> The structural fix is a **feature store**, so training and serving compute features from one definition. Failing that, package the fitted preprocessor with the model, as in [[05 - Packaging Models with FastAPI and Docker]] — one artefact, one transformation, no opportunity for two paths to diverge.

**5.** (Advanced) Design a release plan for a new credit scoring model at a regulated bank, using the deployment strategies and A/B testing. Justify each stage.

> [!example]- Solution
> **A four-stage plan, escalating exposure as evidence accumulates.**
>
> **Stage 1 — Shadow (4–8 weeks).** New model runs on every live application; the incumbent decides. Log both predictions plus the human officer's decision.
> *Why first:* lending is the deck's canonical *"regulatory or safety constraints prevent user impact"* case. Zero applicants are affected while the model is exercised on the true production distribution — including the operational-risk defects of Exercise 4, which only appear when real serving features flow through.
> *Exit criteria:* prediction agreement within tolerance, no training–serving skew, **fairness metrics pass across protected groups**, p95 latency within SLA.
> *Cost:* doubled inference, and no feedback on whether the new model's *disagreements* would have been correct.
>
> **Stage 2 — A/B test on a canary slice (8–12 weeks).** Route **5%** of applications to the new model, randomly assigned.
> *Why randomisation:* it makes the comparison **causal**. Non-random assignment — by branch, or by application time — confounds the model with region or seasonality.
> *The statistical design*, following slide 53:
> - $H_0$: default rate is the same for both models; $H_1$: it differs
> - Two-proportion z-test, $\alpha = 0.05$ → [[Mathematical Statistics/contents/08 - Inferences on Two Samples|Inferences on Two Samples]]
> - **Compute the required sample size in advance.** Detecting a 0.5 pp change in a ~3% default rate needs tens of thousands of applications per arm — which, at 5% traffic, is what sets the 8–12 week duration.
>
> > **The hard constraint specific to credit: label latency.** A loan's default outcome is unknown for months or years. This is [[01 - Introduction to MLOps]]'s delayed-label problem at its most extreme, and it means the primary metric cannot be measured within the test window. Use **early indicators** — 30/60/90-day delinquency, approval rate, PSI by prediction bucket — as leading proxies, and commit to a **retrospective analysis** once true outcomes mature.
>
> **Stage 3 — Progressive canary (25% → 50% → 100%).** Widen only if metrics hold at each step, with automated rollback triggers on approval-rate or fairness-metric deviation.
> *Why not jump to 100%:* the deck's limitation — *"small failures still affect some users"* — is precisely the point. A 5% failure affects 5% of applicants, is detectable, and is reversible.
>
> **Stage 4 — Blue–Green for the final cutover.** Keep the old environment warm for 30 days.
> *Why:* **fast rollback**, and slow-emerging problems (concept drift, a rare applicant segment) may surface after full rollout. The duplicate-infrastructure cost is trivial against the cost of a discriminatory lending finding.
>
> **Throughout — the governance layer**, because this is a regulated model:
> - **Model catalogue entry** — purpose, data, assumptions, risks (step 1 of the evaluation process)
> - **SHAP explainability audits** — regulators and applicants can demand a reason for rejection
> - **Disparate impact monitoring at every stage**, not only at launch
> - **Documented sign-off** before each traffic increase — the human gate of [[09 - CI-CD with GitHub Actions]]'s protected environments
>
> **The unifying logic: each stage buys information at a bounded, known cost in risk.** Shadow costs money and buys correctness evidence. Canary costs a small number of affected applicants and buys causal evidence. Blue–green costs infrastructure and buys reversibility. Skipping stages does not save time; it converts bounded risk into unbounded risk.

## 📝 Summary

- **Deployment faces two challenge categories:** software engineering (compatibility, scalability, latency) and statistical (data and concept drift).
- **Requirements → system design → technology choice**, in that order.
- **Edge vs Cloud** is decided by three questions: how much latency matters, whether connectivity can be relied on, and whether users will send data away. Edge wins on latency, privacy, and offline operation; Cloud wins on throughput and model size.
- **Batch vs online prediction is a separate axis from offline vs online learning.** Batch is simpler and cheaper — prefer it when the use case allows.
- **Big Data's three Vs:** Volume, Velocity, Variety.
- **Validate in an environment that mimics production**, not in development.
- **Model risk has six sources:** data, assumptions/variables, methodology, implementation, interpretation, and **usage** — a correct model used on the wrong population is still a failure.
- **Four deployment strategies:** Shadow (no user impact, doubles cost), Canary (gradual, needs routing infrastructure), Blue–Green (zero downtime, fast rollback, duplicate cost), Rolling (cheap, hard rollback).
- **There is no single best strategy** — it depends on risk tolerance, criticality, and monitoring maturity.
- **A/B testing is hypothesis testing with random assignment**, which is what makes the comparison causal.
- **Deployment is iterative**, not a one-shot launch.

## ⚠️ Important Notes

**Deployment is an iterative process, not a high-stakes single event.** Expect to adjust monitored metrics and traffic percentages continuously. Designing for a perfect launch is the wrong mental model.

**Batch and online *prediction* are independent of offline and online *learning*.** The most common production system trains offline and serves online.

**Prefer batch prediction when the use case permits it** — online serving adds feature retrieval, latency budgets, output validation, and web infrastructure.

**Shadow deployment gives no user feedback.** You learn whether the new model agrees with the old one, not whether its *disagreements* were right — the counterfactual is unobservable.

**Shadow deployment doubles inference cost.** Budget for it.

**Canary failures still affect real users** — a smaller number, which is the point, but not zero.

**Rolling deployment makes rollback hard** and leaves the system temporarily inconsistent across instances.

**Operational risk defeats statistically sound models.** A training–serving feature mismatch produces confident wrong answers that every cross-validation passes. Validate the pipeline end to end, not just the model.

**A model used outside its intended population is a risk source in itself** — the paediatric lung model applied to adults. Correct model, correct implementation, wrong deployment.

**A/B tests need random assignment and a pre-computed sample size.** Assigning by branch or by time confounds the model with location or seasonality; stopping when the result looks good inflates the Type 1 error rate.

**Delayed labels can exceed the A/B test window.** Credit default outcomes take months or years, so the primary metric is unmeasurable during the test. Use leading indicators and commit to retrospective analysis.

**Model risk is not only statistical.** It spans data quality, methodology, implementation, interpretation, usage, and ethics — and fairness must be monitored at every rollout stage, not audited once at launch.

**Every 100 miles from a datacenter costs > 1.6 ms.** For control loops this is decisive; for chatbots it is irrelevant. Know which regime you are in.
