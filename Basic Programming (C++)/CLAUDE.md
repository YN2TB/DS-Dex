- **Ch. 05 — the chapter's centrepiece is the dangling reference, and the result was better than expected.** A returned reference to a local holding **12345 read back as 12289**; a pointer to **54321** read **54273** — *close but wrong*, i.e. plausible enough to survive review and assertions. **Then both changed to 54273 after unrelated calls: the same expression gave different answers with no assignment between.** That is a far stronger statement of what UB means than prose. - **⚠️ RUNNING WARNING-COVERAGE TABLE — five traps, five different answers.** signed/unsigned **warns at /W3**; assignment-in-condition **only at /W4**; stray `;` as loop body **never**; returning a local's address **/W4 (C4172)**; shadowing **/W4 (C4456)**. **Do not infer coverage from one example — test it.** This is the DBMS "a declaration is not an enforcement" lesson, applied to compilers.
- **Ch. 06 — the most valuable cross-subject result in the vault so far. It RESOLVES a question DSA ch. 06 left open.** DSA measured cache locality at only **~15%** in Python and *conjectured* the cause was Python's referential lists (pointers to boxed ints, so both structures chase pointers). **Running the equivalent 4000×4000 matrix traversal in C++ gives 2.5×** (0.0382s row-major vs 0.0965s column-major, identical answers). **The mechanism was real; the language was masking it.** Neither book contains this comparison — it exists only because both subjects are in one vault. **Transferable rule: when a locality measurement disappoints, check the data is genuinely contiguous before concluding the principle is wrong.**
- **Ch. 06 also verified:** array decay (`sizeof` **20 → 8** across a call); `average(a,8)` on a 5-element array returned **−1.45759e+08**; missing `'\0'` made `strlen` return **6** for 5 chars (*plausible*, so it reads as an off-by-one); **`strcpy` of 27 chars into `char[8]` clobbered the neighbour** — `"IMPORTANT"` → `"ing is far too long"`, **and `dest` still printed correctly, so the corrupted variable is the one that looks wrong**; `==` on `char*` gave **false** for identical strings.
- **Precise finding worth keeping: MSVC's `vector` grows by ≈1.5×, not 2×** (1,2,3,4,6,9,13,19,28,42); libstdc++ doubles. Both satisfy DSA ch. 04's amortised argument. **Never rely on `capacity()`.**
- **Warning table now six entries:** add **`strcpy` → C4996 at /W4** (a case where tooling genuinely helps).
- **Ch. 07:** the chapter's spine is **"the compiler writes six special members for you, and whether they're correct depends entirely on your members."** Verified: a struct declaring *nothing* deep-copies correctly (Rule of Zero); **change one member to an owning raw pointer and the same generated copy gives three bugs at once** — aliasing (`b=a` produced the **same address**; `b.data[0]=999` changed `a.data[0]`), dangling, double free. **My framing: the compiler's behaviour is *reasonable*** — it can't know what a pointer means, which is exactly why `unique_ptr`/`shared_ptr` encode ownership in the type. **Sets up ch. 08's Rule of Three directly.**
- **Ch. 07 crisp numbers:** initialiser list = **1 ctor, 0 assigns**; body assignment = **2 ctors, 1 assign**. Padding: `{char,int,char}` = **12** bytes vs `{int,char,char}` = **8** (members total 6; offsets 0,4,8) — **reordering saves 33% free, and compounds into ch. 06's cache-line effect.**
- **Ch. 08 — the subject's core contribution, and its centrepiece is a *measurement* of RAII.** Same function twice, both throwing before cleanup: **raw `new` → live = 1 (LEAKED); `make_unique` → live = 0 (freed).** The `throw` skipped the `delete` (MSVC even said `C4702: unreachable code`) but the destructor still ran during unwinding. **That turns "RAII is good practice" into a result.** Also instrumented: the leak as a *number* (5 constructed, **0 destructed**), Rule of Three giving genuinely different buffers, `shared_ptr` use_count 1→2→1→0.
- **Ch. 08's organising insight, worth reusing:** **every fix removes a manual step rather than making it easier to remember** — `vector` (no form to mismatch), Rule of Zero (no copy functions to write), RAII (no delete-on-every-path), `unique_ptr` (double ownership = *compile error*). **Same principle as ch. 01's `const` and DBMS's constraints, now in four subjects: make the mistake unrepresentable.**
- **Ch. 09 — strangest result in the subject, and it completes a thread from ch. 05.** With default arguments on a `virtual`: **`b.f()` = 100 — the BASE's default (1) with the DERIVED's body (×100).** The body is chosen dynamically, the default statically, so **one call is assembled from two classes and neither author gets what they wrote.** Malik doesn't discuss this; ch. 05 §6 had already established that defaults are substituted statically at the call site, so this is where that fact bites.
- **Ch. 09 also verified:** slicing (`sizeof` **16 → 8**; by-value gave `Shape, area 0` vs `const&` giving `Circle, area 3.14159`; `vector<Shape>` sliced on push_back); **non-virtual destructor ran base=1, derived=0** — the derived `vector<int>` never freed; a virtual call in a constructor resolved to the base; `virtual` cost **8 → 16 bytes**.
- **Ch. 09's synthesis, worth reusing: every trap is a static/dynamic type mismatch** — the compiler consults the declared type and the object is something else, and both are legal so nothing is reported. **Three of the five defences are compile-time** (`override`, abstract base, `protected` dtor), which is the same make-it-unrepresentable principle as ch. 01 `const` and ch. 08 `unique_ptr`.
- **Ch. 10:** centrepiece is the **compile-time vs runtime polymorphism comparison, which Malik never makes** (templates and inheritance are separate chapters). Measured **`sizeof` 8 vs 1** for otherwise-identical empty classes — the 8 is ch. 09's vtable pointer. **The deciding question in the 7-row table: can one container hold a mixture? If yes, only `virtual` can express it.** Also: `operator[]` needs const *and* non-const versions or callers are forced into ch. 05's copies; template errors appear at *instantiation* so messages point into library code (C++20 concepts fix this); `std::vector<bool>` as the specialisation cautionary tale.
- **Ch. 11 (last):** closes ch. 08's arc. **The exception-safety guarantees are absent from Malik entirely** — demonstrated by running the same operation two ways: a failed `appendNoGuarantee` left the object **half-updated (size 6)**, `appendStrong` left it **unchanged (size 3)**. **"Valid but wrong" is the dangerous state** — the caller can't retry, undo *or* trust it. **Cross-subject link that lands: this is DBMS ch. 08's atomicity** — a debit without a credit is exactly this bug, and all-or-nothing is exactly the strong guarantee. Also: `catch` by value slices (ch. 09 again); a destructor throwing during unwinding calls `std::terminate`; **`vector` inspects `noexcept` on your move ctor to decide move-vs-copy on growth**, so one keyword changes every reallocation's cost.
- **The subject's closing synthesis (worth reusing for any language subject):** **every chapter is a case of "the language does something silently and defensibly by default; state your intent so it does what you meant."** Full table is in ch. 11 Exercise 3(d). And **`std::vector<T>` uses every mechanism in the subject** — fixed-width types, RAII, Rule of Zero, operator overloading, templates, `noexcept`, the strong guarantee.
- **Framing established for the subject:** UB means **"no constraints on program behaviour"**, not "unpredictable value" — the compiler may delete an overflow check because signed overflow can't legally happen. Every later chapter should keep labelling UB output as *this machine, this compiler, this run*.

## The angle for this subject

**Python hides three things C++ exposes**: manual memory, value-vs-reference as a choice, and — most importantly — **errors that do not announce themselves**. An off-by-one is an `IndexError` in Python and a plausible wrong number in C++. **That is the same failure mode DSA logged five times and DBMS logged five times; here it is native.** Demonstrate UB, and label results as *this machine, this compiler, this run*.
**Malik predates modern practice** — note the modern form alongside: `std::vector`/`std::string` over raw arrays and C-strings, smart pointers over `new`/`delete`, `nullptr`, range-`for`, `auto`.
